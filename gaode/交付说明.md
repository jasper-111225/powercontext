## 3. 为什么这样写（关键事实核对）

比赛平台统一配置高德 MCP 工具，工具名与参数以官方 `@amap/amap-maps-mcp-server@0.0.8` 为准（本地已解包核对 `build/index.js`）：

- 12 个工具名：`maps_regeocode`、`maps_geo`、`maps_ip_location`、`maps_weather`、`maps_search_detail`、`maps_bicycling`、`maps_direction_walking`、`maps_direction_driving`、`maps_direction_transit_integrated`、`maps_distance`、`maps_text_search`、`maps_around_search`。
- **周边搜叫 `maps_around_search`，不是 `maps_search_around`**（后者是最容易写错的名字，已有 lint 拦截）。
- `maps_around_search` / `maps_text_search` 的返回**只有 `id`/`name`/`address`/`typecode`/`photos`，没有坐标也没有距离**；不补 `maps_search_detail` 就拿不到 `destination`，步行查询必然失败。
- `maps_text_search` 的 `types` 参数在服务端被忽略（handler 只接收 keywords/city/citylimit），所以类型过滤靠关键词 + `typecode`。
- `maps_distance` 是距离测量，**不是步行时间**；题面要求「步行时间应来自路线查询」，故一律用 `maps_direction_walking` 的 `duration`。
- `duration` 单位秒、`distance` 单位米，都是字符串。

## 4. 提交路径（平台是「仓库 + 分支 + commit」，不是文件上传）

平台提测弹窗只有三个字段：**代码仓库地址（锁定为团队仓库，不可改）、Commit id、Branch**。所以 Skill 必须 commit 到 fork 的 `gaode/` 目录，平台按 commit 拉代码后加载该目录。

| 字段 | 填什么 |
|---|---|
| 代码仓库地址 | `https://github.com/jasper-111225/powercontext`（自动带出，不可改） |
| Branch | `2026-competition-ecosystem`（与题面要求同名分支，提交即 fast-forward） |
| Commit id | 该分支最新 commit 的**完整 40 位 SHA**（见 [提测记录.md](../提测记录.md)） |

⚠️ 已实测：该 fork 是**公开仓库**（匿名 `git ls-remote`、GitHub API 均 200），平台可直接克隆，URL 里不需要带 PAT。
若之后把它转成私有，就必须在报名仓库地址里带 PAT，否则评测机 clone 不到（官方 GitHub 使用说明的口径）。

**当前唯一卡点：push 需要的 PAT 无效**——本机 `~/.gh_token` 是 11 字符的占位值（`ghp_` + 7 位），GitHub API 返回 401。

准备与推送（本机已把 commit 打好，只差 push）：

```bash
cd ~/seekdb/source/powercontext
git log --oneline -1 2026-competition-ecosystem        # 确认是 feat(gaode) 那条
git push https://x-access-token:$GH_TOKEN@github.com/jasper-111225/powercontext 2026-competition-ecosystem
```

> 已核对：fork 的 `2026-competition-ecosystem` 当前是 `d647275c`（与上游一致），本条 commit 是其直接子提交，push 是 fast-forward，不会覆盖任何人。
> 不要向 `oceanbase/*` 提 PR（提了不计分，见 [提测记录.md](../提测记录.md) 红线）。
> 时效：AI 判分 + 人工审核，1 天出分；生态题并发 1，别拖到最后一周。

## 6. 已知风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 模型跳过 `maps_search_detail`，拿空坐标查步行 | 数据真实性直接崩 | §1 坑 1、Step 3 单独成步、自检清单第 2 条三重强调 |
| 模型用直线距离/`maps_distance` 估算时间 | 违反题面硬要求 | §1 坑 4 + §5 红线 2 + lint 强制「不是步行时间」说明 |
| 弱模型把超时地点写进表 | 时间限制用例失分 | Step 5 第 1 条 + §4「全部超时」话术 + 自检第 3 条 |
| 搜索半径过小导致候选不足 | 数量不足（不扣满，但少分） | 半径 = W×70 且 ≥500；不足 3 个自动扩半径 ×2 / 换关键词 / text_search 兜底 |
| 平台工具名与 npm 包不一致（如走 Hosted MCP） | 调用失败 | 工具名以官方同一套 12 个为准；若宿主前缀不同，按能力匹配同名工具（Skill 已声明用途而非硬编码前缀） |
| 编造评分/营业状态 | 真实性扣分 | §5 红线 4；缺字段一律「未核实」 |

## 7. 复测方法

拿到分数后按维度看理由：真实性扣分 → 先查是不是没调 detail/walking；需求满足扣分 → 查数量与时间过滤；合理性扣分 → 查排序与理由是否有数据支撑。修改后重新跑 `check_skill.py`，commit 出新 SHA 再提交（同分支追加 commit 即可），单次提测成本低（1 天时效）。
