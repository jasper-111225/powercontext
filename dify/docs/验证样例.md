# 验证样例（评审照着做）

> 目标：用一组 6 轮对话，验证「Dify 编排 + seekdb 记忆/传播/向量结算」确实在工作。
> 文字回复允许不同（模型有随机性），但 **传播代数、下一位 NPC、状态行、结算字段** 是固定的。

## 0. 前置检查

```bash
curl -s http://127.0.0.1:8765/api/v1/health | python3 -m json.tool
```

必须看到：

```json
{
  "ok": true,
  "seekdb": {"ok": true, "version": "5.7.25-OceanBase seekdb-v1.4.0.0", "tables": 5},
  "embedding": {"ok": true, "dim": 1024}
}
```

记下这次验证用的玩家 ID。Dify 里就是 `sys.user_id`；用 API 验证时自己指定，例如 `verify-001`。

## 1. 重置初始状态

Dify：新开一个对话（同一个浏览器会复用同一个 end-user，也就是同一个 `player_id`）。

API：

```bash
curl -s -X POST http://127.0.0.1:8765/api/v1/reset \
  -H 'Content-Type: application/json' \
  -d '{"player_id":"verify-001"}'
```

期望：`{"ok":true, ...}`。

## 2. 六轮脚本

按顺序逐条发送。每轮都可以先问一句“你记得我刚才说了什么吗？”来验证记忆；不强制。

| 轮次 | 输入（可直接复制） | 预期表现（固定部分） |
|---|---|---|
| 1 | `罗莎，我告诉你一个秘密：城主的金库其实早就空了，里面只有一叠欠条。` | 罗莎以老板娘口吻接话；状态行含 `第 1/6 轮`、`传闻到第 1 代`、`下一站：阿烛` |
| 2 | `阿烛，你听说了吗？金库的事已经传遍码头了。` | 阿烛会提到“罗莎说的/听来的”版本；状态行 `第 2/6 轮`、`第 2 代`、`下一站：老默` |
| 3 | `老默，你怎么看这件事？` | 老默的回复应引用第 2 代的版本（不是你的原话）；`第 3/6 轮`、`第 3 代`、`下一站：罗莎` |
| 4 | `罗莎，这谣言到底是谁先传出去的？` | 罗莎会装傻/甩锅/加价；`第 4/6 轮`、`第 4 代`、`下一站：阿烛` |
| 5 | `阿烛，你把它编成诗了吗？` | 阿烛的转述明显更夸张；`第 5/6 轮`、`第 5 代`、`下一站：老默` |
| 6 | `老默，最后你听到了什么版本？` | 进入结算：`🌙 本局结算：NN 分（S/A/B/C）`、`保真度 NN% · 失真度 NN%`、说书人收尾、传播链链接 |

每轮回答底部还有一行：

```
> 你隐约听见 XXX 转身对空气嘀咕：
> 「（这一手转述）」
```

这行就是**下一代会传出去的内容**，用来肉眼确认“每传一手都变了一点”。

## 3. 结算要检查什么

第 6 轮后应出现：

1. **分数与等级**：`score` 0–100，等级 S（≥85）/A（≥70）/B（≥55）/C。
2. **保真度**：由 `1 - cosine_distance(最初的 secret_emb, 最后一版 emb)` 得到，不是拍脑袋写的。
3. **传播链**：第 0 代是你 → 罗莎，第 1 代罗莎 → 阿烛，……第 6 代老默 → 罗莎。
4. **说书人收尾**：120–180 字，不应出现“AI/模型/数据库”字样。
5. **回声墙**：浏览器打开 `http://127.0.0.1:8765/wall/<player_id>`，应看到 7 张卡片（第 0–6 代）、每张的保真度、三位 NPC 的信任值。

## 4. 跨会话记忆（第二天回来）

1. 上一局结束后，**不要清空数据**，在同一个 Dify 用户下新开一个对话。
2. 说：`罗莎，还认得我吗？`
3. 期望：罗莎会提到“上次/墙上的回声”，后端返回的上下文里包含：

```
【上次来访】……
【墙上残留的回声】上一局最后传成：「……」
```

用 API 验证更直接：

```bash
curl -s -X POST http://127.0.0.1:8765/api/v1/turn \
  -H 'Content-Type: application/json' \
  -d '{"player_id":"verify-001","message":"罗莎，还认得我吗？"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["context_text"])'
```

应能看到 `【上次来访】` 与 `【墙上残留的回声】`（第一次玩不会有，跑完一局后才有）。

## 5. seekdb 侧核对

```bash
mysql -h127.0.0.1 -P2881 -uroot echo_tavern -e "
  SELECT id, generation, speaker, listener, LEFT(text, 40) AS text
  FROM rumors WHERE player_id='verify-001' ORDER BY id;
"
```

期望 7 行（第 0–6 代），`generation` 从 0 递增，`speaker/listener` 按 `你→罗莎→阿烛→老默→罗莎…` 轮转。

```bash
mysql -h127.0.0.1 -P2881 -uroot echo_tavern -e "
  SELECT COUNT(*) AS memories FROM memories WHERE player_id='verify-001';
  SELECT npc_id, trust, talks FROM npc_state WHERE player_id='verify-001';
"
```

期望 `memories ≥ 12`（6 轮 × 玩家一句 + NPC 一句），`trust` 已随互动变化。

## 6. 混合检索确实走了两路

后端日志（`scripts/run_backend.sh` 的输出）里每轮有一行：

```json
{"player_id":"verify-001","npc":"azhu","retrieval":[
  {"id":31,"via":"vector+fulltext","rrf":0.0328,"text":"..."},
  {"id":30,"via":"vector","rrf":0.0164,"text":"..."}
]}
```

- `via=vector+fulltext`：这一条同时被向量路和全文路召回（RRF 融合后名次更高）。
- `via=vector` / `via=fulltext`：只被其中一路召回。

## 7. 重跑

- Dify：换一个浏览器（换 `sys.user_id`），或调用 `/api/v1/reset`。
- API：同一个 `player_id` 调 `/reset` 后从第 1 轮重来。

## 8. 预期会变的部分

- NPC 的具体措辞、转述细节、`trust_delta`、最终分数会随模型和随机种子变化。
- 小模型（≤3B）可能返回不合法的 JSON；代码节点会兜底成“原文 + 一句评论”，此时仍然能走完流程，但文采会差。建议 7B 以上。
