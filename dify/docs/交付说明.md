# 交付说明 · 《回声酒馆》

## 一句话

**你把秘密告诉酒馆里的 NPC，他会按自己的性格转述给下一个人；六轮之后，墙把最后听到的版本还给你，并告诉你它歪成了什么样。**

## 1. 创意：把“以讹传讹”做成可玩的机制

传话游戏（telephone game）的乐趣不在“猜对”，而在**亲眼看着一句话被每个人改一点，最后变成另一个东西**。这个作品把这件事做成了三件事：

1. **每一手都真的落库**。传闻不是一个字符串，而是一条 `generation / parent_id / speaker / listener` 的链。你能看到第 0 代到第 6 代，谁在哪一手把“欠条”换成了“仓鼠”。
2. **歪的方向由 NPC 的性格决定**。罗莎往钱上歪，阿烛往诗里歪，老默往短里歪。同一个秘密，交给不同的人，会长出不同的版本。
3. **结算不是评委打分，是向量算出来的**。`cosine_distance(最初的秘密, 最后那一版)` 直接变成“保真度”，再和“传到了几个人”“三个人有多信任你”加权成 S/A/B/C。玩家可以为了刷高分反复玩：先说给谁、什么时候澄清、要不要让老默少说两句。

还有一层：**跨会话记忆**。NPC 记得你上一局留下的传闻。第二天再走进酒馆，罗莎会说“墙上的回声还没散”。

## 2. 一局怎么走

```
第 1 轮  你 → 罗莎：城主的金库其实早就空了，里面只有一叠欠条。
         罗莎（心里）：这话值钱。转身告诉阿烛时，她加了一句“欠条堆得比人还高”。
第 2 轮  你 → 阿烛：你听说了吗？
         阿烛从罗莎那里听来的版本已经开始变形；他转述时又把它变成了“像一颗不肯落地的星”。
...
第 6 轮  老默把最后一版说给罗莎；墙结算：
         保真度 59% · 失真度 41% · 69 分（B）
         说书人收尾 + 完整传播链 + 可打开的回声墙
```

玩家每轮只需要做两个决定：**跟谁说**、**说什么**。规则一眼能懂，但“让谁先知道”“要不要辟谣”“什么时候收手”有策略空间。

## 3. Dify 的分工（核心流程编排）

DSL：[`dsl/echo-tavern.chatflow.yml`](../dsl/echo-tavern.chatflow.yml)，`advanced-chat`，11 个节点 / 10 条边：

| 节点 | 作用 |
|---|---|
| Start | 接收 `sys.query` / `sys.user_id`（Dify 的终端用户 ID 就是玩家 ID） |
| 酒馆回信（HTTP） | `POST /api/v1/turn`：取这个 NPC 的记忆、信任、最近听来的版本 |
| 拆开酒馆的回信（Code） | 把 HTTP 响应拆成 `npc_name / persona / style / context_text` 等变量 |
| NPC 即兴演出（LLM） | 人设 + 本轮情境 + 硬性要求；输出 `{say, retell, trust_delta, mood}` |
| 整理 NPC 的 JSON（Code） | 剥代码块、取第一个 JSON、字段兜底（模型不听话也能继续） |
| 记进墙里（HTTP） | `POST /api/v1/commit`：写入这一手转述、更新信任、判断是否散场 |
| 看墙的回执（Code） | 拆出 `phase / status_line / finale_context / score` 等 |
| 是否散场（IF/ELSE） | `phase == done` → 说书人；否则正常回话 |
| 说书人收尾（LLM） | 用 seekdb 算出的传播链写 120–180 字收尾 |
| 酒馆里 / 打烊（Answer） | 两种终局输出 |

为什么用 **Chatflow** 而不是 Workflow：这是一个多轮对话，玩家会连续输入；Chatflow 的 `sys.query` / `sys.user_id` 与 Dify 自带聊天界面刚好够用，不需要另写前端。

## 4. seekdb 的分工（数据 + 检索 + 结算）

不是“装了个数据库”，而是三个功能点都依赖它：

| 用途 | 表 / 能力 |
|---|---|
| 游戏状态 | `players`（当前秘密、轮次、局数）、`npc_state`（每个玩家对每个 NPC 的信任）、`npcs`（人设种子） |
| 传闻传播链 | `rumors`：每代一行，`parent_id` 指向上一个版本；带 `FULLTEXT ... WITH PARSER ik` 与 `VECTOR INDEX ... HNSW` |
| 对话记忆 | `memories`：玩家/NPC 说过的每一句，同样带全文与向量索引 |
| 每轮取上下文 | `hybrid_memories()`：向量路 `ORDER BY cosine_distance(emb, ?)` + 全文路 `MATCH(text) AGAINST(?)`，RRF 融合 |
| 结算 | `cosine_distance(secret_emb, final_emb)` → 保真度；传播覆盖率与平均信任参与加权 |

一条实际跑出来的检索日志（`docs/evidence/`）：

```json
{"npc":"azhu","retrieval":[
  {"id":31,"via":"vector+fulltext","rrf":0.0328,"text":"..."},
  {"id":30,"via":"vector","rrf":0.0164,"text":"..."}
]}
```

Dify 自己的 Postgres 仍由官方 compose 提供；**seekdb 承担的是应用数据、记忆与检索**，符合题面“为应用提供数据存储、查询与检索能力”的选项。

## 5. 完成度

- 6 轮完整局 + 结算 + 说书人收尾 + 回声墙（HTML）。
- 每轮两种结局分支；模型 JSON 不合法时自动兜底，不会卡死。
- 跨会话：上一局结束后自动开新局，保留 NPC 信任与旧传闻，并在上下文里回调。
- 重置：`POST /api/v1/reset`，方便评审反复跑同一脚本。
- 运维可见性：`/api/v1/health` 同时检查 seekdb 与 embedding；每轮日志带检索来源。
- 交付自检：`check_dsl.py`（连线/变量/代码节点）、`check_with_graphon.py`（Dify 1.18 同款引擎判定可加载）、14 个单元测试。
- 文档：运行说明、6 轮验证样例、实际运行证据、seekdb 表结构。

## 6. 已知边界

- 本地参考环境没有 Docker，**没有在 Dify UI 里截图**；DSL 用 Dify 1.18 自带的 graphon 0.8.0 引擎做了 `inspect`（`status: loadable`），并用本地排练器按同一份 DSL 跑完整局。正式体验仍需按 README 导入 Dify。
- DSL 版本写的是 0.3.1（与 Dify 1.18 仓库自带测试夹具一致）；1.18 导入时会提示“版本较旧”，选择继续即可。
- 参考实现用的是本机 7B 模型，文采有限；换 DeepSeek / Qwen 等更强模型，NPC 会更像人。玩法机制与模型无关。
- 传闻的“歪”由 LLM 完成，极端情况下可能歪得不够明显（后端会检测逐字相同并补一句），但不会中断流程。
- 没有做多人房间、语音、独立前端；入口就是 Dify 的应用界面。

## 7. 原创与参考
