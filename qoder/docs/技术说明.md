# 技术说明

> 这份文档写给想核对「技术是否真的在起作用」的评审：数据怎么落、检索怎么走、
> 引用怎么校验、记忆怎么持久化，以及为什么这样取舍。

## 1. 数据模型

```sql
CREATE TABLE documents (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  title VARCHAR(200) NOT NULL,
  source VARCHAR(512) NOT NULL,          -- 文件路径 / 上传路径，唯一
  kind VARCHAR(16) NOT NULL,             -- markdown | pdf | html | text
  pages INT NULL,
  chars INT NOT NULL DEFAULT 0,
  checksum VARCHAR(64) NOT NULL DEFAULT '',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_doc_source (source(191))
) ORGANIZATION = HEAP;

CREATE TABLE chunks (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  doc_id BIGINT NOT NULL,
  ordinal INT NOT NULL DEFAULT 0,
  heading VARCHAR(255) NOT NULL DEFAULT '',  -- 标题路径，如「编译生产二进制」
  page INT NULL,                              -- PDF 页码
  text TEXT NOT NULL,
  embedding VECTOR(1024) NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_chunk_doc (doc_id, ordinal),
  FULLTEXT INDEX ft_chunk (text) WITH PARSER ik,
  VECTOR INDEX vi_chunk (embedding) WITH (DISTANCE=cosine, TYPE=hnsw, LIB=vsag)
) ORGANIZATION = HEAP;
```

`queries` 存问答日志（引用快照为 JSON），`notes` 存收藏。四张表同库，便于一次连接完成「检索 → 作答 → 记日志」。

### 1.1 分块策略（`app/ingest.py`）

- Markdown 按 `#/##/###` 维护标题栈，块内保留完整标题路径；块目标 760 字符，上限 1050，同标题内 110 字符重叠。
- 优先在段落边界切；超长段落按 `。！？；` 切句，再按字符硬切。
- 代码围栏不单独丢弃：`_pack` 保留原样，`llm._sentences` 在抽取时把围栏内容并回「……：」后的说明，得到
  `编译产物位于：build_release/src/observer/seekdb` 这样的完整证据句。
- PDF 按页抽文本，`page` 落库；HTML 去 `script/style` 后按段落切。

### 1.2 为什么保留 `heading` 和 `page`

引用不能只给「某篇文档」，否则等于没给。`heading` 让人知道在文档的哪一节，`page` 让 PDF 能翻回去。
前端证据卡的副标题就是这两者的组合。

## 2. 混合检索

### 2.1 两路召回

向量路：

```sql
SELECT c.id, c.doc_id, c.ordinal, c.heading, c.page, c.text,
       1 - cosine_distance(c.embedding, %s) AS vec_sim
FROM chunks c
ORDER BY cosine_distance(c.embedding, %s) ASC
LIMIT 30;
```

全文路：

```sql
SELECT c.id, ..., MATCH(c.text) AGAINST(%s IN NATURAL LANGUAGE MODE) AS ft_score
FROM chunks c
WHERE MATCH(c.text) AGAINST(%s IN NATURAL LANGUAGE MODE)
ORDER BY ft_score DESC
LIMIT 30;
```

两路都支持 `doc_id` 过滤（资料库侧栏选中某篇时生效）。

### 2.2 RRF 融合

```python
score(d) = 1 / (60 + rank_vector(d)) + 1 / (60 + rank_fulltext(d))
```

只使用排名，不使用原始分数：余弦相似度和 BM25 分数不可比，RRF 免去调权重。
`60` 是常用平滑常数，让头部排名差异更明显。

**为什么不是「向量 + 关键词」简单相加？** 中文技术文档里，`--init`、`build_release/src/observer/seekdb`
这类串向量模型几乎无感；而口语化的问题（「怎么排查内存问题」）全文又匹配不到原文措辞。两路互补，
在 23 题评测里全文路单独能救回若干向量漏掉的命令/路径题。

### 2.3 置信度与拒答

```text
coverage   = 问题词（中文 bigram + 英文词）在前 3 条证据中的出现比例
confidence = min(1, top_vec_sim * 0.75 + coverage * 0.45)
拒答条件   = top_vec_sim < 0.28 且 coverage < 0.20
```

阈值可通过 `JUDIAN_MIN_VECTOR_SIM` 调整。拒答不是异常，是产品行为：资料外的问题必须说「没有依据」。

## 3. 作答与引用校验（`app/llm.py`）

1. 取 Top-8 片段，编号 `[1]…[8]`，附文档名、标题路径、页码；
2. 提示词要求「只依据材料、每句带编号、材料不足只说固定句」；
3. 模型返回后：
   - 若前 40 字包含「资料中没有找到足够依据」→ `insufficient`；
   - 提取 `[n]`，越界编号删除；一个合法引用都没有 → **抽取式兜底**；
4. 抽取式：把每个片段拆成句子（代码块并回说明），按「问题词覆盖² + 向量相似度 + 排名 + 问句类型」
   排序，去近似重复（3-gram Jaccard > 0.5），取 3 句，逐句带 `[n]`；
5. 返回 `mode`：`llm` / `extractive` / `insufficient`，前端如实标注。

> 0.5B 模型经常直接抄代码块或忽略编号，所以**校验是硬性的**：没有合法引用就不采用模型文本。
> 这不是「降级」，而是研究场景更需要的可核验性。

## 4. PowerContext 记忆

### 4.1 Scope 与条目

```text
Scope: title=judian-learning, summary=据典 · 个人资料问答的学习主题、偏好与进度
  ├─ kind=judian-profile   {topic, style, goal, saved_at}
  └─ kind=judian-progress  {asked, last_question, last_confidence, last_mode,
                            last_docs[], weak_topics[], updated_at}
```

- 首次调用 `POST /v1/scopes` 创建，`idempotency_key` 防重复；scope_id 缓存在 `.runtime/powercontext_scope.json`；
- 写入 `POST /v1/memory/remember`；读取 `POST /v1/memory/entries/list`，按 kind 取最后一条；
- 单条记忆限制 8KB，代码里做了字节数校验。

### 4.2 为什么记忆放 PowerContext 而不是 seekdb

seekdb 适合「可检索的资料」，PowerContext 适合「关于人的、会演进的状态」：Scope 隔离、版本、
生命周期、后续可接自动提取。两者职责不同，放在一起反而职责不清。

### 4.3 降级

PowerContext 不可用（未启动、超时、鉴权失败）时，`Memory.save()` 写 `.runtime/memory_fallback.json`，
`snapshot()` 读最后一条，返回 `source=local`；前端显示「本地暂存」。问答主流程不受影响。

## 5. 性能

验证机：4 核 / 9.7 GB，无 GPU。

| 环节 | 典型耗时 |
|---|---|
| 向量化一个 chunk（Ollama 0.6B，CPU） | 0.8–3.5 s（取决于负载） |
| 查询向量化（模型已加载） | 0.3–0.8 s |
| 两路检索（138 片段） | 20–60 ms |
| 抽取式作答 | < 5 ms |
| 小模型生成 | 8–25 s（常被校验拒绝，故默认不依赖） |
| 端到端（抽取式） | 0.6–1.5 s |

向量索引 HNSW 在 138 片段规模下优化器可能仍走精确扫描（数据量小），但 SQL 与索引已经就绪；
片段数到万级时会走 `vi_chunk`。

## 6. 安全与边界

- 上传限制 20MB、后缀白名单；文件名清洗后落 `data/uploads/`；
- SQL 全部参数化；库名做白名单正则；
- 不写任何密钥到仓库；PowerContext token 是本地演示值；
- 只支持单用户（`JUDIAN_USER=demo`），多用户需要把 user_id 贯穿到表和 Scope；
- 答案不构成事实保证：引用可核验，但片段本身可能有误，界面明确提示「只依据你的资料」。
