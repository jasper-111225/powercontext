**输入**

```bash

```

**实际**

```json
{"ok":true,"db":"ok","corpus":{"documents":9,"chunks":135,"chars":52711,"avg_chunk_chars":398.3},
 "vector":true,"llm":true,"memory":"ok","memory_source":"powercontext"}
```

页面「资料库」标签显示每篇资料的片段数、字符数（截图 `docs/evidence/screens/library.png`）。

```sql

SHOW CREATE TABLE chunks;        -- 含 VECTOR INDEX / FULLTEXT INDEX
```

## 场景 2 · 编译产物：双路召回 + 引用

**输入**

```bash
curl -s -X POST http://127.0.0.1:8766/api/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"Release 模式的编译产物在哪个目录？"}'
```

**预期**：答案包含 `build_release/src/observer/seekdb`，`citations` 非空，证据里同时出现向量排名与全文排名。

**实际**（`mode=extractive`，置信度 0.6714，8 条证据 / 2 条引用）

```text
根据《获取代码、编译并运行 seekdb》的原文：
- 编译产物位于： build_release/src/observer/seekdb [1]
- 与 Release 模式相同，增加 `--make` 可以在配置后直接编译： ./build.sh sanity --init --make -j32 [3]
- 完成初始化后，可以使用以下命令进行增量编译： ./build.sh release --make [1]
```

| # | 来源 | 标题路径 | 向量排名 | 全文排名 | RRF | 是否引用 |
|---|---|---|---:|---:|---:|---|
| 1 | 获取代码、编译并运行 seekdb | 编译生产二进制 | 3 | **1** | 0.032266 | ✅ |
| 3 | 获取代码、编译并运行 seekdb | 编译 Sanity 二进制 | 6 | **2** | 0.031281 | ✅ |

**技术作用**：全文路把「编译产物」精确命中的段落排到第 1；向量路把语义相近的调试文档排到第 1；
RRF 后构建文档的两段进入答案。`[1]` / `[3]` 可点击，右侧对应证据卡高亮；点「查看完整原文」显示未截断文本。

## 场景 3 · GDB：证据集中在一个文档

**输入**：`怎么用 GDB 调试 seekdb？`

**实际**（`mode=extractive`，置信度 0.8877，2 条引用）

```text
根据《调试 seekdb》的原文：
- 在 GDB 中加载实际找到的文件： symbol-file /absolute/path/to/seekdb.debug [1]
- 在 Linux 上查找进程并附加 GDB： pidof seekdb [2]
- 分析 core dump 时，必须使用生成该文件的同一二进制： gdb /path/to/seekdb /path/to/core [2]
```

证据 1（`调试 seekdb › 使用 RPM debuginfo`）：向量 #1 / 全文 #3；
证据 2（`调试 seekdb › 使用 GDB 或 LLDB`）：向量 #6 / 全文 #2。

**技术作用**：两条证据都来自 `debug.md`，标题路径直接指出是「使用 RPM debuginfo」与「使用 GDB 或 LLDB」一节；
`heading` 让引用能落到具体小节，而不是只说「某篇文档」。

## 场景 4 · 资料外问题：拒答

**输入**：`seekdb 支持 MongoDB 协议吗？`

**实际**（`mode=insufficient`，`citations=[]`）

```text
资料中没有找到足够依据来回答这个问题。换一种问法，或把这个主题的资料导入资料库后再试。
```

响应里的 `reason`：

```text
资料中没有出现：mongodb（不做语料外推断）
```

**技术作用**：问句中的英文实体 `mongodb` 在 135 个片段里不存在，直接拒答；
即使向量检索仍会返回若干「相似」片段，也不会拿它们拼答案。
另外两道不可答题（GPU 加速、Kubernetes Operator）同样被拒，见评测 `u01–u03`。

## 场景 5 · 记忆：写入 → 重启 Server → 读回

**输入**

```bash
curl -s -X POST http://127.0.0.1:8766/api/memory/profile \
  -H 'Content-Type: application/json' \
  -d '{"topic":"seekdb 内核开发：从编译到调试","style":"concise","goal":"读完内存与日志文档，跑通一次本地编译"}'

# 重启 PowerContext
scripts/pc_server.sh restart

curl -s http://127.0.0.1:8766/api/memory
```

**预期**：重启后 `profile.topic` 仍是「seekdb 内核开发：从编译到调试」，`entries` 数量不减少。

**实际**

```json
{"connected":true,"source":"powercontext","scope_id":"scp_3d05bvecj5m7e9pawx2r19zvtg",
 "entries":39,
 "profile":{"topic":"seekdb 内核开发：从编译到调试","style":"",
            "goal":"读完内存与日志文档，跑通一次本地编译"},
 "progress":{"asked":31,"last_question":"Release 模式的编译产物在哪个目录？",
             "last_mode":"extractive","last_docs":["实验笔记","编程惯例"]}}
```

页面右上角「我的学习记忆」显示同一份数据（截图 `docs/evidence/screens/memory.png`）；首页横幅显示
「我记得：你在研究 seekdb 内核开发：从编译到调试 …」。

**PowerContext 作用**：写入走 `POST /v1/memory/remember`（kind=`judian-profile` / `judian-progress`），
读取走 `POST /v1/memory/entries/list`；数据在 `.runtime/powercontext-home`（SQLite），进程重启不丢。
本机实际经历过一次 7 小时后的服务重启，`/api/memory` 仍返回上述主题与条目。

## 场景 6 · 导入自己的资料并引用

**输入**

```bash
curl -s -X POST http://127.0.0.1:8766/api/import \
  -F 'file=@data/samples/实验笔记.md'

curl -s -X POST http://127.0.0.1:8766/api/ask \
  -H 'Content-Type: application/json' \
  -d '{"question":"我在容器里编译 seekdb 时依赖下载卡住了，后来怎么解决的？"}'
```

**预期**：导入返回 2 个片段；回答引用《实验笔记》，而不是官方文档。

**实际**

```json
{"ok":true,"doc_id":3000001,"title":"实验笔记","kind":"markdown","chars":463,"chunks":2}
```

```text
根据资料原文：
- 在容器里跑 `./build.sh release --init` 时，依赖下载卡在 73%，重试后命中缓存才继续。 [1]
- 由于seekdb支持多租户资源隔离，为了方便控制内存，seekdb禁止使用STL、boost等容器。 [2]
- 否则 CMake 缓存里的绝对路径会和容器内路径冲突。 [1]
```

证据 1：《实验笔记》› 2026-10-22 · 一个坑（RRF 0.032522），`used=true`。

**技术作用**：新资料在几秒内完成分块、向量化、入索引；下一次提问即可被检索到并作为 `[1]` 引用。
验证结束后已删除该资料，保持演示语料 9 篇 / 135 片段。
