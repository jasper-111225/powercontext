# 性能优化实践

端侧知识库的性能可以拆成五段：模型下载与加载、文档向量化、写入与索引刷新、查询向量化、检索排序。分阶段计时比只报一个端到端数字更有诊断价值，因为优化手段完全不同。

模型加载的优化点包括：把模型文件放在本地静态目录，避免公网 CDN；开启 HTTP 缓存；不要每次查询都重建 pipeline。加载完成后做一次预热推理，把 shader 编译和缓冲区分配的成本提前付掉。报告时应区分冷加载和预热后的状态。

文档向量化的优化点是批处理和进度反馈。批大小 8 到 16 通常能跑满 CPU 或 GPU；批太大反而增加内存压力和首条延迟。每批完成后更新进度条，用户不会觉得界面卡死。吞吐用“块/秒”和“字符/秒”两个口径报告，因为分块长度会变化。

写入与索引刷新的优化点是减少往返。把分块按 100 条一批 upsert，最后一次 refresh_index。如果每写一条就刷新，索引维护成本会主导总耗时。导入大文件时，可以先写完所有批次再刷新，刷新期间界面提示“索引合并中”。

查询路径的优化点是减少不必要的计算。查询只编码一次，向量复用；检索只发一次 hybridSearch，不在客户端做二次排序；TopK 控制在合理范围，候选窗口不要无限放大。端到端延迟 = 查询向量化 + 网络往返 + 数据库检索 + 前端渲染，四段都要单独记录。

复测时要固定设备、浏览器版本、语料、查询集、批大小和后端。同一份代码在不同机器上差异可能很大，报告里必须写清楚环境。每个实验至少重复 3 轮，报告中位数，同时给出 P95，避免只挑最快的一次。首次请求和预热后要分开报告。

最后，优化不能以牺牲检索质量为代价。每次性能改动后重跑质量评估；如果 Recall@K 明显下降，说明优化改变了语义，需要回滚或补偿。
